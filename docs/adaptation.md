# Platform Adaptation Notes

Hands-on experience and pitfalls from moonbit-libyue's adaptation on each platform, all verified in real environments.
The main AI document (repo root `AGENTS.md`, read by ZCode) pulls in this file via `@docs/adaptation.md`; this document is the continuously updated, detailed version of platform adaptation pitfalls (the README keeps only a pointer and does not elaborate).

**Organization dimensions**:

- Linux follows a three-level scheme: "distribution -> desktop environment -> version";
- Windows / macOS follow "version".

- ⚠️ Partially usable or conditional

## Cross-Platform (build chain / FFI, platform-independent)

### Build and Linking

- Keep the habit of running `moon` commands from the **repo root**: although link arguments have been switched to absolute paths (see below), runtime lookup of vendor/build artifacts and WebView2Loader.dll still depends on the working directory.
- moon's `link` section only applies to the package it resides in and only takes effect for main-package binaries; putting a link section in a library package (such as `yue/`) makes moon generate a main-less `.exe` and breaks the build. Link configuration has been fully consolidated into `scripts/prebuild.py`; no package's `moon.pkg` writes `cc-link-flags` anymore.
- **Manifest migration to the new `moon.mod` / `moon.pkg` format (verified 2026-09-15)**: new moon versions deprecate `moon.mod.json` / `moon.pkg.json`; `moon fmt` migrates in one step (fields become DSL-style: `preferred_target`, `options(...)` blocks; pkg imports/targets migrate accordingly). `moondoc` / `moon doc` only recognizes the new format — mooncakes 0.1.0's "Documentation failed to generate" was caused by the server-side moondoc not finding `moon.mod`; publishing a new version number after migration restored it. Note: older moon (stable 20260904 etc.) does not recognize the new format, so consumers need a fairly recent toolchain.
- **Link arguments for both platforms are propagated by the pre-build hook (current approach, verified 2026-09-12)**: moon's `cc-link-flags` is a single string and `targets` conditional compilation has no OS dimension, so link arguments cannot be stored per-platform. Current mechanism: `moon.mod` declares `--moonbit-unstable-prebuild: scripts/prebuild.py`; moon executes it on every build, the script outputs a `link_configs` JSON based on `platform.system()`, and moon **automatically propagates it to all main packages that depend on the yue package** — this repo's examples and mooncakes consumers need zero configuration, and switching platforms swaps arguments automatically. Field-tested key points:
  - The script's **stdout may contain only the final JSON**: any print (including passthrough from subprocesses) makes moon's deserialization fail (`invalid number at line 1 column 2`); progress messages must go to stderr.
  - **Do not put libyue_mbt in `link_libs`**: when moon assembles the command line, `link_flags` comes before `link_libs`; GNU ld resolves left to right, so `-lyue_mbt` placed after `-lstdc++` yields `undefined reference to __cxa_guard_acquire`. Put all arguments in `link_flags` as a single string to control the order yourself (same order as the old response file).
  - The script's cwd is **moon's invocation directory (the consumer project root)**; to locate itself it must use `Path(__file__)`; the propagated library paths must be **absolute paths** (the cwd of the link command is on the consumer side).
  - When build artifacts are missing, the script automatically invokes prepare.py to rebuild them (returns in milliseconds when artifacts exist); the first build downloads from GitHub.
  - This mechanism is officially marked experimental (`--moonbit-unstable-prebuild`); the API may change with moon upgrades; availability of the `python3` command on Windows is pending real-machine verification.
  - Historical approaches: first, writing back moon.pkg.json per OS (the two platforms overwrote each other) -> then an `@build/link.flags` response file (both gcc/clang and cl support `@file`; one shared file for both platforms). Both have been superseded by the propagation mechanism.
- `prepare.py` is idempotent and re-runnable: a cache zip with mismatched sha256 (truncated download) is deleted and re-downloaded automatically; downloads go to a `.part` temp file first and are atomically placed only after checksum verification. Networking honors the standard `http_proxy/https_proxy` environment variables.
- **moon does not automatically relink when static libraries change (cross-platform, verified on Linux 2026-09-15)**: prebuild invokes prepare only when a static library is **missing**, and moon's relink decision only looks at MoonBit sources and the link_configs output, not at static library contents — after re-running prepare following shim/vendor changes, the linked artifact still points to the old library. For detection and handling see [docs/relink.md](relink.md).
- **Three ways for newly added shim functions to die (verified on Linux 2026-09-16, fixed on the Linux side)**: the ~90 shim functions added by the "method-level audit backfill" batches (09-16) were never compiled into the Linux side of the library, and any MoonBit call failed to link. Three compounding causes: (1) the whole block of functions was mistakenly enclosed in the `#else (non-Linux)` branch of the `sys_*` platform conditional (that branch should only contain the sys stubs); (2) the function definitions lacked `extern "C"`, so the symbols were renamed by C++ name mangling and the ffi could not resolve them by C name; (3) the `extern "C"` block in `yue_mbt.h` was closed early at line 602, leaving the new declarations at lines 605-697 outside the block (C++ linkage), conflicting with the definitions on the cpp side. The block also hid six classes of genuine compile errors behind "moved into the non-Linux branch": the Window focus signal names (`on_focus`/`on_blur`, lambda parameter `Window*`), a duplicate MessageBox `set_informative_text`, `Table::Notify*` being a private API (the GTK model notifies views automatically — Linux stubs are no-ops), `Appearance::SetDarkModeEnabled` being Windows-only, the audit block misusing `CastTo<>` where the corresponding `XStore::get()` was required (some classes have no `kClassName` on Linux), and `base::JSONWriter` requiring an explicit `base/json/json_writer.h` include plus constructing `ValueView` by reference. Fixes: narrowed the `#endif` to the end of the sys stubs, wrapped the audit block in a single `extern "C" {}`, moved the header's closing brace to the end of the file, and corrected the six error classes one by one. **Bar for adding shim functions: must compile fully on Linux + be declared inside the extern "C" region of `yue_mbt.h` + verify via `nm` that the symbol exists under its C name (any `_Z` prefix means `extern "C"` is missing)**. Verified: after the fixes, Windows compiled the whole block for the first time and showcase/components ran correctly (2026-09-16) — the six error classes were exposed by that very first Windows compile.
- **MSVC misreads BOM-less UTF-8 sources under cp936, producing fake "unexpected #endif" errors (verified 2026-09-16)**: on a machine with ACP=936 (GBK), the two-byte sequences of Chinese comments swallow the following characters (such as a leading `#` on the next line), breaking preprocessing directives; the reported line contains no `#endif` at all. Fix: add `/utf-8` for MSVC in CMake (both source and execution character sets). This hits any BOM-less UTF-8 source with Chinese comments on Chinese-locale Windows, regardless of code content.
- **A shim drag helper leaked GLib APIs to Windows (verified 2026-09-16, exposed by the first Windows compile of the audit block)**: `MakeFilePathsForDrag` used `g_get_current_dir()` (GLib, Linux only) with no platform guard. Fix: split out `CurrentDirForDrag` (Windows: `GetCurrentDirectoryA`) and `IsAbsPathForDrag` (Windows: drive-letter `C:` plus `/` and backslash), with a per-platform separator. Lesson: before pulling a system library into audit-block/new shim functions, confirm its availability on the target platform — the GLib family (`g_*`) is Linux-only.
- **Stale static library after shim FFI additions: `undefined reference to yue_mbt_*` (cross-platform, verified on Linux 2026-09-16)**: when shim/FFI sources change without re-running `prepare.py`, the old `build/libyue_mbt.a` lacks the new symbols and any program using the new API fails to link — verified 2026-09-16: shim gained `get_bounds_in_screen` / `label_set_align` / `view_set_visible` on 09-16 while the library was from 09-15, and `moon run examples/showcase` failed to link outright. Two aggravating factors: (1) prebuild only rebuilds when the library is **missing**, never when stale; (2) small examples like hello do not reference the new symbols and link fine, faking a "build is fine" impression — always verify with showcase. This was initially misattributed to a moon nightly 0911 test-build regression (corrected after comparing library vs shim symbols with `nm`). Fix: re-run `python3 scripts/prepare.py`, then `moon clean` to force a full relink. Detection: `nm build/libyue_mbt.a | grep <new symbol>` returning nothing means the library is stale. See the related entries above and [docs/relink.md](relink.md).
- **Old static libraries silently swallow shim fixes; real-machine re-tests show "the fix doesn't work" (cross-platform, hit on Windows 2026-09-16)**: after Windows fixes (set_borderless inverted logic, on_scroll deferral, all in shim) were pushed, the user's `git pull + moon clean + moon build` test still reproduced the old defects — `moon clean` only clears `_build`, while `build/yue_mbt.lib` was the old library; prebuild's "rebuild only when missing" check let it pass, so the relink still used pre-fix code. Fix: prebuild.py gained a `_shim_newer_than_lib` guard — when shim sources (`shim/*.cpp|*.h`, `shim/include/*.h`) have mtimes newer than the static library, it automatically runs `cmake --build` incremental recompile (no vendor re-download / full prepare re-run needed) and prompts deleting the exes under `_build` to trigger a relink. From then on, shim changes take effect on `moon build` automatically; only vendor/prepare.py patch changes still require manually running prepare.py.
- **The `postadd` script is triggered only when installed via registry `moon add`**; path/git dependencies and building the module itself do not trigger it; the fallback for missing artifacts is handled by prebuild.py's checks. Since the vendored libraries went live, `postadd` has been removed: registry installs use the binaries shipped with the package directly, with no install-time actions needed.
- The libyue version is pinned in `scripts/prepare.py` (`LIBYUE_VERSION` + six sha256s: source release zips for three platforms + prebuilt libraries for three platforms); upgrading requires updating the checksums in sync. Upstream has switched from yue/yue to the fork lb091188/yue (see the next bullet).
- **Upstream switched to the fork (lb091188/yue) + a prebuilt-asset pipeline (recorded 2026-09-18)**: the original approach downloaded the official yue/yue release zip and applied 13 vendor patch sets locally, making upgrades/reproduction heavy; now all patches live as standalone commits in the fork (main == upstream v0.15.6), and the fork CI (`prebuilt.yml`, triggered by `v*-mbt*` tags) produces six assets: source release zips for three platforms + prebuilt static libraries for three platforms (linux-x64 / mac universal lipo binary / win-x64), published directly to releases (draft assets cannot be downloaded anonymously). prepare.py switched to "prebuilt first, source fallback": `LIBYUE_FORCE_SOURCE=1` forces source; platforms without assets (linux/arm64) fall back automatically; `build/prepare_stamp` records "version mode", prebuild checks staleness to prevent linking old artifacts, and source mode clears leftover prebuilt libraries to avoid duplicate symbols. The win release zip bundles the WebView2 SDK headers + loader DLL in the fork (upstream ships only the bare DLL), and the NuGet completion logic was removed wholesale. Pitfalls: a fork-side `no_destructor.h` typo blows up mac **at build time** (newer Xcode clang instantiates that template member), and the fix must be applied in `bootstrap.js` immediately after the submodule checkout (too late at packaging time); win submodule checkouts are CRLF, so normalize line endings before patch matching; on case-insensitive volumes the `webview2.h` alias is the same file as `WebView2.h`, so probe for existence and skip before copying.
- **Clang-built libyue + gcc-built shim mixed linking: stable runtime segfaults (hit on Ubuntu 24.04 2026-09-18, the core pitfall of the prebuilt pipeline)**: symptom: after the prebuilt `libyue.a` (clang-built) from the fork CI (ubuntu-22.04) was integrated, `moon run examples/hello` segfaulted 5/5 at line 10 of `moonbit_main` at `set_content`, with the stack stopping at `gtk_container_add <- nu::Window::PlatformSetContentView`; the occasional graceful exit on the first run was more deceptive. Controlled experiment (same machine, same sources, only the compiler varied): gcc lib + gcc shim pass / gcc split layout + gcc shim pass / clang lib + gcc shim fail / clang lib + clang shim pass — **the static library and the shim must come from the same compiler family**; mixing families (even with identical Itanium ABI and libstdc++, both libstdc++) always crashes on this libyue codebase; root cause not dug deeper (suspected hidden divergence in header inline-code layout/behavior across compilers). Fix: the fork's `prebuilt.yml` Linux job no longer switches cc/c++ to clang (that step was inherited from upstream CI, which is all-clang upstream with no issue); prebuilt libraries are built with gcc; mac (clang/clang) and win (MSVC/MSVC) are naturally same-family. Also: 22.04 toolchain artifacts need an explicit `-latomic` at final link (`__atomic_store`; the official dist CMakeLists already links atomic), and prebuild.py's Linux link arguments have been updated.
- **Vendored binaries distributed with mooncakes (since 2026-09-18, modeled on justjavac/quickjs)**: `lib/{linux-x64,macos-universal,windows-x64}/` contain the shim library + prebuilt libyue (+ win's manifest.res and loader DLL); prebuild.py cascades "vendored -> build/": with vendored in place there is zero C++ compilation; when shim sources are newer than the vendored library it automatically falls back to the build/ development flow; the three-platform artifacts are fixed per-platform by this repo's `vendor-native.yml` (triggered by `vendor-*` tags), gathered via release assets, and pulled with `python3 scripts/vendor_native.py --fetch <tag>` on the maintenance machine and committed. The development flow (prepare/source fallback) is unchanged.
- **Since 2026-09 the moon toolchain fully deprecates "implicit promotion of trait methods onto the type" (recorded 2026-09-19)**: the tightening of `implicit_impl_as_method` landed on the `moon test` / `moon build` (full native compile) paths — `moon check` does not report it and incremental compilation does not re-report; only a clean full run shows everything: all 488 `obj.method()`-style implicit ViewLike calls in the repo warned (which is how the earlier "check 0 warnings" commit gate slipped through). Fix: repo-wide batch migration to explicit static calls `ViewLike::method(obj, args)` (493 sites: 486 by script + 7 by hand; the `obj.(ViewLike::method)()` restricted form wrongly reported Type Mismatch in that version and was unusable). **Always write new component code directly in the `ViewLike::xxx(obj, ...)` form**; the batch-migration script's regex did not recognize `arr[i].method()` indexed receivers (5 mis-cuts fixed by hand), and any rerun of the same migration needs an indexed-receiver variant first. Verification: after clean, check/test/build all zero warnings, 33/33 tests, both example smoke runs alive.
- **The implicit-promotion deprecation formally landed at impl declaration sites + a new warning for unqualified references in black-box tests (recorded 2026-09-21, closing out the leftovers of `02550cf`)**: starting with moon 0.1.20260920, `moon check` (clean full run) reports two new warning classes, equally missed by incremental builds: (1) `implicit_impl_as_method` (E0079) points at the **impl declaration sites** themselves — 18 `pub impl ViewLike for X` in `yue/types.mbt`, `derive(Eq, Debug)` in `yue/icons.mbt`, `impl Show for TrayError` in `yue/error.mbt`, 21 sites in total (the 19 sites reported by 0911 were the same batch's overture, back then reported only on the check path and shelved as "forward tightening"); (2) `test_unqualified_package` (E0025) at 60 sites — unqualified references to package-internal functions/constants/type names (such as `Signal`, `RectF`, `KEY_MOD_CTRL`, `argb_hex`) in black-box `*_test.mbt` files; they must be written `@yue.xxx` / `@traybus.xxx`. Fixes: (1) at impl sites, add explicit `pub extend X with Trait::{...}` **per type** following the compiler diagnostics, with method lists generated verbatim from `moon check --no-render` output by script, never hand-copied (Window's list naturally lacks `set_background_color` — it has its own same-named method; the short form `pub extend X with Trait` without a method list is not valid syntax); (2) in test files, change only the unqualified references **on flagged lines** (same-named words inside test-title strings are not on flagged lines; a whole-file regex replace would misfire). Toolchain note: the new moon's `moon fmt` rewrites 44 files repo-wide per the new rules (format drift, unrelated to the fixes) — not mixed into that batch. Verification: after clean, check zero warnings, test 45/45, build native passes, hello/showcase smoke runs alive — showcase's sidebar `set_visible`, page `set_style`, panel `set_background_color` all go through promoted methods, actually executed at runtime, extend declarations work end to end.
- **Changing shim without re-publishing -> vendored lags a generation; git-checkout mtimes always misjudge and trigger the fallback (hit on Win10 2026-09-19)**: symptom: `1cdef9d` (MouseEventScreenPoint, mouse trampolines 7->9 args) changed only shim without re-running vendor packaging, leaving the three-platform vendored libraries at `56aa944`, one generation behind — the MoonBit layer already used the 9-arg extern while the vendored library still had the old 7-arg symbols, so the zero-compile path inevitably fails with undefined reference; and git clone/pull writes files in **path order**, so `lib/` always lands earlier than `shim/` (by milliseconds), making `_sources_newer`'s mtime comparison misjudge "the developer is modifying shim" **after every pull** and fall back to the build/ rebuild flow — a plain shell without the MSVC environment gets stuck at CMake's INCLUDE check. The fallback direction happened to dodge the broken old library, but the Windows rebuild exposed that commit's GTK symbols missing a guard (see the 2026-09-19 entry in the Windows section). Three-layer fix: (1) added `OS_LINUX` guards to two shim definitions; (2) `_sources_newer` switched to **git-based recency**: uncommitted shim changes count as new, otherwise compare the last commit times of `shim` vs `lib/<platform>` (mtime comparison only as a fallback in non-git environments); (3) ran `vendor_native.py` in a vcvars64 environment to backfill `lib/windows-x64` (linux/mac still a generation behind, to be aligned via `--fetch` after the `vendor-*` CI produces packages; until then Linux/mac consumers automatically take the source-fallback path). Lesson: **commits that change shim must backfill at least the local platform's vendored library in the same batch and align all three platforms via CI as soon as possible**, otherwise "zero-compile ready-to-use" is a broken link for users. Verification: in a plain shell (no MSVC environment), `moon check` zero warnings, `moon test` all passing, `moon build examples/showcase` links vendored directly with zero C++ compilation, showcase smoke run alive.

### MoonBit cfg(platform=) platform conditional compilation

- **Current state (recorded 2026-09-14)**: moonc already implements `#cfg(platform="windows"/"linux"/"macos")` conditional compilation (not documented officially); evaluation is based on the `-target` **triple** passed to moonc (`x86_64-unknown-linux-gnu` / `x86_64-pc-windows-msvc` / `aarch64-apple-darwin`); the `not/any/all` combinators work. moonbitlang/openseek uses it in production (only `platform="windows"` and its negation).
- **However, the currently installable moon builds (stable 0.1.20260904 and nightly 0.1.20260911) only pass the generic `native` without OS info to moonc**, so all `platform=` conditions are constantly false — on Linux even `platform="linux"` does not hit; `MOONBIT_NEW_NATIVE=1` and the new `moon.mod` format (the direct-object-file backend is in effect, producing .o) also do not pass the triple. The moon main branch already has logic to select the triple by host (`NativeTarget::from_host`: x86_64 Linux / Apple Silicon enabled by default, Windows requires env=1); **the conditions will light up only once a release carries it**.
- Migration signal: add `-v` to any build; once `x86_64-unknown-linux-gnu` appears as `-target` in the moonc command line, it is usable; at that point showcase's runtime platform sections can be replaced with `#cfg` in one line.
- Current substitute: runtime `platform()` checks — the declarative tree assembles nodes conditionally and simply does not create controls when a condition fails, which is equivalent to compile-time hiding; showcase's platform sections (desktop environment, clipboard primary selection, custom protocol, etc.) use this approach, see the header comment in `examples/showcase/section.mbt`.
- Verification method: in a temporary project build and run both branches (`#cfg(platform="linux")` / `#cfg(not(platform="linux"))`) to see which one is taken; invoking moonc directly with `-target x86_64-unknown-linux-gnu` proves the compiler side already works (in testing, each of the three branches landed where expected). Also: file-level `targets` in `moon.pkg.json` still only has backend (wasm/js/native) + debug/release dimensions; feeding it an OS value fails schema loading outright; bare-identifier conditions (e.g. `#cfg(linux)`) are always true and meaningless.
- Side note: nightly 0911 emits 19 `implicit_impl_as_method` deprecation warnings for the repo-wide `impl ViewLike for X` (stable 0904 does not) — forward tightening by the toolchain, not a library regression; formally landed and fixed with moon 0.1.20260920 on 2026-09-21, see the last entry of "Build and Linking".

### Declarative layer and self-drawn components

- **set_background_color inside mouse_enter/leave callbacks rewrites runtime CSS and swallows the immediately following first press (real-machine verified 2026-09-19)**: backtop_t once expressed its hover background via set_background_color in the hover callback (the GTK implementation is ApplyStyle adding a CSS provider) — real-machine symptom: after scrolling to the bottom, the first click "didn't budge" and only the second click scrolled back to top; i.e. the first press was swallowed by the event-window disturbance. All other self-drawn widgets in the library express hover by reading the palette on demand in on_draw (backtop was the last escapee). Fix: the hover background is now expressed in on_draw (hover state paints a darker primary), enter/leave only set state + schedule_paint, zero CSS rewrites. **Rule: set_background_color is forbidden at runtime (inside mouse callbacks); hover/pressed and other interaction states are always expressed in on_draw; set_background_color is only allowed at mount time and inside theme-subscription callbacks.** Also: for "takes two clicks to work" bug reports, first distinguish "didn't budge" (event layer: press swallowed) from "flashes back and bounces again" (value set was pulled back by an in-flight scroll event; use a short set_timeout re-set as a backstop) — the fixes differ.
- **Container child attach order = flex layout order = z order; sandwich widgets (handles/separators) must be attached strictly in layout position (recorded 2026-09-19)**: the first Splitter version attached the handle before the two panes (due to mount-point adjustments mid-implementation), making the layout order "handle, second pane, first pane" — the handle was laid out into an 8px sliver at the container's far left, visually "no separator bar in the middle"; from the user's perspective that is "can't drag + can't find the drag area"; the event system itself was fine (click/drag logic all present, just the handle wasn't where the user expected). Fix: strict pane_a -> handle -> pane_b attach order, and the handle visual made always-visible (central 1px separator line + double-dot texture, not hover-dependent), light-grey fill on hover, theme-color fill with white dots while dragging. **Lessons: (1) a flex container's attach order must never be adjusted as "affects only z order" — it is simultaneously the layout order; (2) interactive self-drawn sandwich widgets must be always visible, not hover-revealed — users find them by looking, not by touching; (3) to debug this class of issue, a probe example + xwd screenshot of the real rendered layout is fastest — layout chaos shows up in one screenshot (xdotool synthetic drags are incompatible with GTK motion recognition; drag-type interactions go by the real machine).**

### MoonBit <-> C ABI

- **The arity of the FuncRef+Callback trampoline must match the C function-pointer prototype argument for argument** (verified 2026-09-11). Convention: C calls `callback(closure, args...)`, and the MoonBit trampoline is `fn(f, args...)` where the first parameter `f` receives the closure.
  - Case: Table's `get_value`/`set_value` trampolines each carried one extra argument versus the C prototype (4 vs 3, 8 vs 6); after argument misalignment the ModelBox was invoked as a function pointer -> segfault on first render; whereas `row_count` (1 vs 1) was correct, so row counts were fine and the window could be created — **some interfaces "appearing to work" can mask arity misalignment**; a callback counts as verified only after it has actually fired once.
- `extern "c"` cannot return nullable types (ABI incompatible with C pointers, immediate segfault): report success/failure via a `Ref[Int]` out-parameter and return handles as non-null.
- FFI pointer parameters must be marked `#borrow` (compiler-enforced); multiple parameters of the same function go into a single `#borrow(a, b)`.
- Control parameters in extern declarations must use the underlying handle type `View`, not a MoonBit wrapper struct (such as `Slider`): what crosses the ABI for a struct is the wrapper object, not the handle value, and at runtime everything reports "invalid handle" and is silently dropped (the Slider/Table families were wholly broken by this; 22 sites fixed in 2026-09).
- Closures crossing the C ABI: only capture-free top-level function literals are allowed (compiled into real C function pointers); closures with captures use the "function pointer + closure pointer" two-parameter pattern (the `on_click` family).
- Callback closures are kept alive by a registry (`yue/view.mbt`); entries are not reclaimed after window destruction — **the decision is to keep them alive for the process lifetime** (2026-09-12): there is no ownership relationship between callbacks and windows to follow, precise reclamation would need a weak-reference registry, and the current MoonBit ecosystem is not mature; the leak is negligible for single-window tool scenarios (decided 2026-09-12).
- **Toolbar / Vibrant are unavailable on Linux**: the libyue headers have no platform guard, but the Linux static library does not compile in any related symbols (nm shows zero symbols in testing), so calling them fails at link time; the Binding side is explicitly marked as not exposed.
- **Browser::GetCookiesForURL FATALs on an empty cookie list**: libyue 0.15.6's internal `CHECK(cookies)` crashes outright on an empty list (upstream defect) — WebKitGTK legitimately represents an empty GList as NULL, so on vendored mbt.6 and earlier, querying a URL with no cookies always crashed; fork v0.15.6-mbt.7 removed the assertion (empty lists call back normally, aligned with the Windows semantics); the assets have since shipped (vendored is now mbt.12), so the restriction is lifted — querying a cookie-less URL calls back with an empty list.
- **Changing a shim function signature must update `include/yue_mbt.h` in the same batch, otherwise the breakage manifests as a "mangle split" rather than a straightforward error (verified 2026-09-19)**: all declarations in `yue_mbt.h` sit inside `extern "C" {}`, and .cpp definitions inherit C linkage via the include — once a header declaration is left stale, the .cpp's new-signature definition no longer matches the old declaration; C++ treats it as an overload and exports it with C++ mangling (`_Z26yue_mbt_view_on_mouse_down...`), while the MoonBit side always references the plain C name -> `undefined reference to 'yue_mbt_view_on_mouse_down'`. The intermediate investigation is easily misled: the hundreds of other symbols in the library are plain C names (header-inherited), only the few new-signature ones are mangled; an nm comparison locates it. Fix = change header, .cpp, and ffi.mbt signatures in the same batch (the event screen-coordinate expansion 7->9 args hit exactly this). Variant (verified 2026-09-20): a new FFI written only as a .cpp definition with the header declaration missed entirely — same mangle split — `yue_mbt_tray_set_image` (introduced in e0df994) lurked two months untriggered until the demo board added a `Tray::set_icon` demo and hit the broken link; this variant is more insidious than "changed signature, forgot to sync" (not a missed change but entirely missing), and a pre-packaging scan of "all .cpp function definitions x header declarations" catches it in advance (static/GTK internal callbacks excepted).
- **Two-layer root cause of SNI tray icon changes "not working" (real-machine verified on XFCE 2026-09-20)**: neither of the demo board's "switch to theme icon / switch back to image" buttons produced any visual change. (1) `set_icon_name` had already emitted the NewIcon signal, but the item still carried the program's built-in IconPixmap — the XFCE panel prioritizes **IconPixmap over IconName**, and after re-reading properties it kept painting the old pixmap; fix = clear the pixmap when setting icon_name (w=0/h=0/empty bytes) and conversely clear icon_name when setting pixmap, keeping the two mutually exclusive. (2) The SNI branch of `Tray::set_icon` was a no-op (no PNG decoding); fix = the shim gained `yue_mbt_image_read_argb32` (GdkPixbuf static frame -> the big-endian ARGB32 SNI requires, RGB padded with 0xFF alpha, row stride repacked); the MoonBit side pre-allocates `Bytes::make(w*h*4)` and passes it #borrow, and on success does set_pixmap + NewIcon — header/cpp/ffi all written in the same batch (to prevent a mangle-split recurrence). Verification: on the real machine, clicking "switch to theme icon" changed the tray to the system terminal icon, and "switch back to image icon" restored the icon.png bitmap.

### DBus wire-protocol pitfalls (traybus field tests, desktop-environment-independent)

- The DBus array length prefix **does not include the alignment padding before the first element**: counting it in is judged a protocol violation by dbus-daemon, which drops the connection.
- The variant signature of the DBus header SIGNATURE field is "g" (u8 length encoding); encoding it as "s" passes self-consistent unit tests but is rejected by the real bus.
- **The SNI `Menu` property must always return a real menu object path; even an empty menu must not return `/`**: the GNOME AppIndicator extension reads this property at the instant of registration to build its proxy, and returning `/` permanently kills the menu client (see the "GNOME" section); the Qt/ksni semantics are to always export `/MenuBar`.
- Lesson: **unit tests prove self-consistency; interop must be verified on the real bus**; diagnose discovery-type issues by capturing packets with `dbus-monitor`, and for JS exceptions on the extension/panel side check `journalctl --user -u org.gnome.Shell@wayland.service` (gnome-shell's Gio.DBusError lines are the first crime scene of proxy-construction failure on the panel side).

### GTK-related

- Putting a Table (GTK) inside a Notebook tab segfaults during size negotiation (negative allocation); it must go into a plain container or a standalone window (showcase uses standalone subwindows; reproduced in showcase on 2026-09-11: before the crash, `Negative content width -1 (… owner GtkFrame)` and the `GtkScrollbar` `size >= 0` assertion appear first).
- **Composite controls (Tab/Scroll/Group) are "leaf nodes without a measure function" in the yoga tree; their outer dimensions must be given explicitly (flex/width/height), otherwise they collapse**. Field test (2026-09-14, Ubuntu 24.04 + XFCE, after the declarative showcase rewrite): changing `Tab` from being the window content directly (`SetContentView`, entering no yoga tree) to being attached under the root `Container` left the whole tab area blank below the tab strip and uninteractive, with logs `gtk_box_gadget_distribute: assertion 'size >= 0' failed in GtkNotebook` + `Negative content width -1 … owner GtkFrame`. Root cause in three layers: `Tab::Tab()`'s constructor bakes the then-current `GetMinimumSize()` (empty notebook ≈ tab-header height) into yoga minWidth/minHeight via `UpdateDefaultStyle()`; `AddPage` only sets the View-level parent and **never refreshes that value** (an upstream libyue limitation); with no flex, a leaf node's height stays at the baked value, so the notebook page area = allocated height - tab header <= 0. Fix: give the `tab()` node `("flex", 1.0)` (yoga only governs the outer frame; tab pages do not enter Tab's yoga tree — `AddPage` performs no yoga insertion; each page container is the root of its own independent yoga subtree, with GTK allocating the page area). Note that `scroll_page` was initially misdiagnosed as a within-page issue (490826b controlled experiment); the collapse was in the notebook's outer frame and unrelated to within-page layout.
- **The content of content-type controls does not go through `AddChild`**: `Group`/`Scroll` inherit directly from `View` (not `Container`); content must be attached via their own `SetContentView`; going through `Container::AddChild` is rejected by the shim's `CastTo<Container>` type check (log: "type mismatch, expected Container, got Group/Scroll") and the content is silently lost. That is why the declarative layer's (`yue/declarative.mbt`) `group()`/`scroll()` nodes first mount the content into a temporary `Container` and then `set_content` the whole block. Transient `GtkNotebook` assertions at page-switch moments remain in small numbers after the fix (start-up/page-switch transient layout noise, CRITICAL but not fatal); all UI functionality has been restored.
- **Seam defects of the GTK backend's NUContainer (verified 2026-09-14/15; patches in `prepare.py patch_linux_container_events`)**. Exposed by the declarative rewrite wrapping Tab in a root `Container` and adding a `holder` container per page (the old Tab was the window content view directly and never went through these paths): (1) in `nu_container_map` the event window used `gdk_window_show` (= map + **raise**), lifting the INPUT_ONLY window covering the whole container above child native controls — X/GDK hits got intercepted, so **tab headers were unclickable and the scroll wheel dead, while buttons/keyboard were fine** (keyboard goes through focus; the windows of buttons/editable controls are mapped later and lifted higher); switching to `gdk_window_show_unraised` only maps without raising. (2) `nu_container_get_preferred_width/height` hardcode a return of 0, and GtkViewport computes the scroll range from the child's size_request (written as 0x0 upstream) -> the scroll range is always 0 and no scrollbar appears. **Do not "fix" this by reporting yoga's dynamic natural size to GTK** — allocate pollutes yoga state and causes requisition-negotiation oscillation (measured 365->466->598->907, non-converging, layout stuck on an intermediate frame, pages "sometimes not filling the width"); the correct fix is in (3). (3) `Scroll::PlatformSetContentView` forced the size_request from `GetPixelBounds()` = 0x0 for unmounted views; changed to: without an explicit `SetContentSize`, width stays -1 (stretches with the viewport) and height is fixed to the content's yoga natural height (queried via `Container::GetPreferredSize` after discriminating with `IsContainer()`) — the scroll range converges in one pass and is correct. The `CreateEventWindow` typo where `attributes.y` was wrongly assigned `allocation.x` was also fixed.
- **The `IsVisibleInHierarchy` guard at the start of `Container::UpdateChildBounds` makes independent yoga roots miss the first real allocation (verified 2026-09-15, same patch function)**. GTK's first size-allocate happens **before** map, when overall visibility is false -> the guard returns immediately; after map nobody re-runs the yoga layout with the real allocation, so independent yoga roots (each page's holder, the Scroll content container) permanently stay at their mount-time natural-size layout — page content "sometimes" does not fill the container width (whether it reproduces depends on subsequent resize re-allocations). Fix: remove the overall guard and run the layout computation unconditionally (`GetBounds()` reads the GTK allocation already updated by the size_allocate vfunc, so early layout is safe; GTK also permits pre-allocating unmapped widgets); child bounds propagation is still subject to each child's visibility; `nu_container_size_allocate` adds a `gtk_widget_queue_draw` when the allocation changes.
- **The lingering ignore flag in `Slider::SetValue` broke slider linkage (verified 2026-09-15, same patch function)**: dragging the slider on Linux left the progress bar and the bound label unmoved. `Slider::SetValue` unconditionally sets the `ignore-value-change` flag to prevent callback loops, but GTK emits no `value-changed` for "setting the same value" (the yue layer's `Slider::make` defaults to `set_value(0)`, and the initial value is already 0) -> the flag lingers and the first callback of the user's first drag is swallowed; the xdotool single-tap jump-value scenario emits exactly one signal, manifesting as total failure. Fix: set the flag only when `GetValue() != value`.
- **Platform difference in the value range of `ProgressBar::SetValue` (verified 2026-09-15, fix in shim)**: libyue's Linux `SetValue` semantics are 0..100 (internally divided by 100 again), while the yue layer unifies on 0..1 -> the progress bar only reaches 1% (`v/100` then divided by 100 again). The conversion branch now covers Linux+Windows: Win's ProgressBarImpl sets no PBM_SETRANGE so the control default range is 0..100 — same symptom verified on Windows 2026-09-16 (bar only reached 1%).
- **`View::GetBoundsInScreen` stacked coordinates wrongly under Scroll/nested containers (all Linux desktops, verified 2026-09-15, patch `patch_linux_view_bounds_in_screen`)**: the upstream implementation manually accumulates allocations at each level, mixing in viewport document coordinates — with the showcase page scrolled to the middle-lower part, the anchor y measured 1221 (screen only 1080 tall), placing the bubble off-screen, manifesting as "the bubble shows only when maximized, never otherwise". Fix: switch to `gtk_widget_translate_coordinates` + the window origin (GTK natively understands viewport scrolling and nesting), keeping the original logic as a fallback. - **Drag-out root cure: source-side signals were never installed + drag_context never written back (XFCE real-machine verified 2026-09-20, fixed in fork v0.15.6-mbt.12)**: mbt.10/11 changed nothing symptom-wise; controlled reproduction (xdotool-synthesized press/move/release, state written to files via `write_text_file` for communication — **MoonBit println is silent under pipe/file redirection; instrumentation must not use stdout**) advanced to "the ghost appeared but the receiver showed zero response": not one of drag-data-get/drag-end/drag-failed fired. Smoking gun in the source: **the source-side signals are installed only in `RegisterDraggedTypes` (a receiver-side API), never called in a pure drag-out scenario** — the target's data request went through GTK's empty class handler (no files received; the desktop highlight was only visual feedback on the session), nobody handled drag-end so the nested `gtk_main` never exited (the true root cause of "only one drag", i.e. the context lingered but the cause was the missing signals); moreover `drag_context` was not written back after begin, so even with listeners the exit branch would not fire. Fix (mbt.12): DoDrag captures the press event (`gtk_get_current_event`; must be GDK_BUTTON_PRESS or it returns NONE), arms motion/release handlers, and after crossing the 8px threshold starts `gtk_drag_begin` **with the press event** (an X grab needs the press timestamp; a NULL event with GDK_CURRENT_TIME gets rejected by the server's auto press-grab — the direct cause of death); the drag image is set after begin; releasing below the threshold ends as no-session. #### Link arguments (actual moon -> cl/link behavior, all field-tested)

- **`cc-link-flags` is concatenated verbatim into the `cl` command line**, not passed directly to link: GNU-style `-L/-l` yields D9002/D9024; `/LIBPATH:` is likewise a compiler option cl doesn't recognize and is only warned about, not forwarded. **The correct approach is to write link inputs**: `build/yue_mbt.lib setupapi.lib …` — cl passes positional .lib/.res arguments to link; system libraries are resolved via the `LIB` environment variable injected by vcvars, no arguments needed.
- **Separators must be forward slashes**: `build\yue_mbt.lib` has its backslash eaten as an escape by moon's argument parsing, and link receives `buildyue_mbt.lib`, yielding LNK1104.
- The official CMakeLists' system library list is itself incomplete (missing user32/ole32/oleaut32/shell32 etc.); copying it directly yields 144+ LNK2019s (DefWindowProcW/VariantClear/SysStringLen etc.); `prepare.py`/shim lists have been completed with the GUI basics — link ignores surplus libraries.
- **The CRT must match moon's static /MT**: the code generated by moon is fixed to `/MT` (debug included). CMake multi-config generators **ignore `CMAKE_BUILD_TYPE`**, and `cmake --build` without `--config` builds Debug (/MDd) by default, ultimately failing the link with LNK4098 (MSVCRTD conflict) + about 200 unresolved `__imp__*`. Fix: shim library `cmake_policy(SET CMP0091 NEW)` + `CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded` (must be set before add_library) + build with `--config Release` (automated in prepare.py).
- **moon does not automatically relink when static libraries change**: when neither cc-link-flags nor MoonBit sources changed, after swapping `yue_mbt.lib`, `moon build` reports "no work to do"; touch any source file of the main package to force a relink.
- **CI-released Windows exe shows a black console window on double-click (fixed 2026-09-20, visual effect pending re-verification on a real machine)**: the release-bin trio (hello/hello-themed/showcase) kept a black console alongside the GUI window when double-clicked. Root cause is on the moon side: its Windows backend link template (`link_executable_command` in crates/moonbuild-rupes-recta, verified in moon's source) assembles the cl command as `cl /Fe… <objs> /link /nologo /subsystem:console /LIBPATH:… <propagated link_flags> <default libs>` — `/subsystem:console` is hardcoded, so the exe ships as a console-subsystem binary and Windows attaches a console on launch. Fix: prebuild.py's Windows link_flags now starts with `/SUBSYSTEM:WINDOWS`; the propagation mechanism places it after the hardcoded `/subsystem:console`, and link.exe lets the last occurrence of the same switch win. No `/ENTRY` needed — when unspecified, link picks the entry from the symbols actually defined, and moon's standard `main` maps to `mainCRTStartup` (`cl /subsystem:windows` + main is a long-standing idiom). This does not contradict the D9002 note in the first bullet: cl only consumes compiler options outside the `/link` section, and this flag lands inside it, straight to link. Side effects: with the GUI subsystem, stdout is invisible in interactive terminals (pipe/file redirection still works); moon test captures output via pipes and is unaffected; the Windows CI job only builds and tests (no GUI smoke), so the pipeline is indifferent. 'Local verification: the Linux branch's output does not contain the flag (zero cross-platform impact), a simulated win32 branch emits link_flags starting with `/SUBSYSTEM:WINDOWS`, and full check/test/build pass with zero warnings. **Disproved on re-verification (2026-09-21, PE headers of the bin-v0.4.1 artifacts)**: all three exes still had OptionalHeader.Subsystem = CONSOLE(3) — **link.exe takes the FIRST /SUBSYSTEM when duplicated**; moon's link template (`crates/moonbuild-rupes-recta/src/build_lower/compiler/msvc.rs::link_executable_command`; moon's own unit test asserts the hardcoded switch is present) places `/subsystem:console` before the user's link flags, so appending `/SUBSYSTEM:WINDOWS` cannot override it; there is no official switch, and no upstream issue has ever been filed. The responsibility is the moon toolchain's — not libyue's, not this repo's. Product-side stopgap: release-bin.yml patches the PE header Subsystem 3->2 after the Windows artifacts land (equivalent to `editbin /SUBSYSTEM:WINDOWS`; the entry point was already resolved to mainCRTStartup at link time, which calls main normally under the GUI subsystem — no change needed); the prebuild flag is retained to take effect automatically once upstream fixes the template. The console window on consumers' self-built exes can only be fixed upstream (a subsystem switch in moon's template, or honoring the user's flag). **Re-verified again + official suggestion put to the test (2026-09-21, CI real MSVC link on the experiment/win-gui-pragma branch, three-way controlled experiment: hello with no stub as control / hello-themed pure pragma / showcase pragma + referenced symbol)**: the previous "hardcoded /subsystem:console + first-wins" mechanism inference was wrong — the evidence-corrected story: for ordinary exes moon assembles the link command via `make_cc_command_resolved_for_toolchain` (moonutil/src/compiler_flags.rs), where the user's link_flags are concatenated **before** `/link` (the user string is extended first, then `/link /LIBPATH` is pushed), so prebuild's `/SUBSYSTEM:WINDOWS` is dropped by cl.exe as an unknown compiler option (`cl : Command line warning D9002 : ignoring unknown option '/SUBSYSTEM:WINDOWS'`, confirmed in the verbose log) and never reaches the linker at all. The hardcoded `/subsystem:console` only exists in `link_executable_command` (the other, `lower_link_new_native_exe` path), which this repo's builds never take — the actual path carries no /subsystem at all, and CONSOLE(3) comes purely from the linker's "main is defined, so default to CONSOLE" rule. The maintainer's suggested C-side `#pragma comment(linker, "/SUBSYSTEM:WINDOWS")` + `"/ENTRY:mainCRTStartup"` was tested in the same run: **the mechanism works, with a precondition** — the pragma lives in the object's drectve section, and moon compiles a package's native-stub sources into a static archive (CStubLibrary) placed in the sources segment of the link command, where link.exe only processes the drectve of **extracted members**: (a) pure pragma with no symbols (hello-themed) → the member is never extracted → CONSOLE(3), no effect; (b) pragma + referenced symbol (showcase, whose main forcibly references the stub's `yue_mbt_gui_marker`) → the member is extracted → GUI(2) with a successful link (both pragmas take effect simultaneously; without /ENTRY the link would fail with unresolved WinMain). Conclusion: **library-wide automation is feasible** — put the pragma stub into the yue package (`"native-stub"`) and have yue's own code (e.g. initialize) reference a stub symbol to guarantee extraction; every consumer depending on yue then gets the GUI subsystem with zero configuration, while binaries that never reference the symbol (moon test etc.) are unaffected. **Shipped (2026-09-21, merged after the experiment/win-gui-productize branch verified all three exes GUI(2) on CI)**: the yue package now carries win_gui.c (native-stub, pragma + the `yue_mbt_win_gui_marker` symbol), with `initialize()` referencing that symbol so the archive member is extracted; release-bin.yml's PE-header rewrite is demoted to a fallback (skipped when already GUI(2)); prebuild.py dropped the `/SUBSYSTEM:WINDOWS` dead parameter that never reached the linker, which also eliminates the D9002 noise. mooncakes consumers get the effect automatically once they upgrade to a release containing this change.

- The `dlfcn.h` include needs an `__linux__` guard (the use site is already inside an `OS_LINUX` block); MSVC's `M_PI` needs `#define _USE_MATH_DEFINES`.

Root cause: `56aa944`'s "entry normalization" introduced `yue_mbt_entry_new_ex`, whose `#else` (non-Linux) branch forwards to `yue_mbt_entry_new_typed`, whose only implementation forwards back to ex — the Linux branch really creates the control so it is symptom-free; on Windows/mac creating any Entry infinitely recurses -> stack overflow -> caught by the shim's process-level exception hook (SetUnhandledExceptionFilter, from the ghost-tray cleanup) and turns into a **livelock**: the exception handling itself overflows again, manifesting as "process alive, CPU spinning, never crashing" — highly deceptive. **The compiler had been saying so all along: MSVC C4717 "function will cause a stack overflow at runtime" is exactly this pair of functions — the warning appeared when vendored was first built on Windows, but that library had never run on Windows** — lesson: treat C4717-class "logically certain death" warnings as errors. Fix: entry_new_ex's non-Linux branch directly does `new nu::Entry` (the Linux branch minus the GTK width_chars part); after rebuilding, C4717 disappeared. Verification: rebuilt vendored + `moon clean` relink (moon does not auto-relink on static-library updates, see above); showcase/components windows both appeared (MainWindowHandle != 0), CPU back to zero. Methodology on record: (1) to diagnose a GUI "no window", PowerShell's `Get-Process <name> | Select MainWindowHandle` is the headless verdict tool (0 = no visible window; combined with CPU it distinguishes "spinning stuck" from "quietly waiting"); (2) when stdout is redirected to a pipe, MoonBit `println` is fully buffered and the buffer is lost if the process is killed — "empty log" does not mean "did not execute"; do not rely on println for instrumentation; (3) showcase's window title showing "Showcase — https://www.moonbitlang.com/" is the classic behavior of the browser page's IE/WebView2 host control rewriting the host window title after navigation (the browser page loads on mount); no such phenomenon on Linux — a cosmetic known difference pending real-machine re-verification. Also, the "display relies on activate() at the end of mount_window's handle callback" contract recorded here was voided on 2026-09-20: hello-themed's missing manual activate caused "process alive, window not appearing"; mount_window now auto-activates and shows after the handle runs, so consumers no longer activate manually.
- **The input's top-hugging text and theme-independence, both cured at once (fixed 2026-09-19, visuals pending real-machine re-verification)**: (1) top-hugging: Win32 single-line EDIT/RICHEDIT paints from the client top with no vertical-centering style (known since 09-17; autocomplete's height-22 compression was the stopgap then, and that component was removed with the d9cfb39 refactor). The thorough fix (goal "native input vertically centered, cross-platform look consistent", sizes derived from actual font metrics, not hardcoded): the component-layer `entry_vcenter` — measures the font line height with AttributedText, narrows the native control to "line height (+1px x 2 when it has a native border)", and splits the remaining height evenly into top/bottom margins; wired into `entry_t` (new height parameter defaulting to 30) / `input_t` (the outer frame line 1px x 2 deducted from the available height; a borderless control's height = line height) / the declarative `entry` (Windows intercepts the height style and applies the same decomposition, defaulting to 30 without height, and unifies the Sans13 font so the line-height measurement matches the control's actual font; other platforms pass styles through untouched). (2) theme colors: the Windows native RichEdit is permanently black-text and does not follow theme_apply (Linux is covered by the global takeover CSS; the problem is Windows-only). Added `yue_mbt_entry_set_colors` (full chain shim->header->ffi->`Entry::set_colors`): Windows goes EM_SETBKCOLOR + CHARFORMAT2 (clearing CFE_AUTOCOLOR and enabling crTextColor; SCF_DEFAULT affects only new text — existing text is re-set once per the new default and re-laid-out — the channel verified by the probe dark-mode experiments); Linux uses a per-control GtkCssProvider (priority G_MAXUINT over the global takeover CSS; the provider is stored in the widget data slot for reuse, so repeated theme switches do not stack); mac a no-op. The component layer's `bind_entry_theme`: on non-Linux sets theme_text_regular/theme_bg_panel and subscribes to on_theme_change to re-set. **A MoonBit FFI Bytes parameter needs the `#borrow` attribute on its own line (parameter names listed on the line before the extern declaration); writing it in the parameter position is a syntax error**. Verification: check/test/build zero warnings all green, both example smoke runs alive; the vertical centering and the input's light-on-dark under the dark theme pending real-machine re-verification (the components demo board is dark-themed — the input area is the most direct).
- **Popups/dropdowns close on outside click, completed (fixed 2026-09-19, interaction pending real-machine re-verification)**: the Windows replacement popup previously had no click-outside-close (only the 8-second backstop + the component's focus_out, neither firing when clicking non-focus areas), so all Popover-based dropdowns (select_t/dropdown_menu/calendar_t/date_picker_t etc.) manifested as "you must pick an option to collapse", whereas the Linux GTK Popover's native input grab carries click-outside-close natively. Fix (pure shim, no ABI change): while the popup is shown, a WH_MOUSE_LL low-level mouse hook is installed — if the press point is outside the popup's rectangle (GetWindowRect; the LL hook's pt is likewise in physical pixels), collapse via `MessageLoop::PostTask` (not touching the GUI directly inside the hook to avoid re-entrancy; the task captures the popup pointer at trigger time and does nothing if a new popup has replaced it by execution; the event is not swallowed — CallNextHookEx passes it on, the click still reaches its original target); collapsing is unified in `HideActivePopover`: unhook + kill timer + SetVisible(false) reusing the window + Emitting on_close per the GTK Close semantics (already hidden not re-emitted — fixing "hook-collapse and component focus_out-collapse double-emitting the signal"), and the 8-second backstop path likewise re-emits on_close (previously a silent hide on timeout, leaving component state unrecovered and lurking "after timeout it never opens again"). Also fixed a latent prebuild NameError: `except (SameFileError, ...)` — the name was never imported — **Python evaluates the except list only when an exception actually occurs**; this bug lurked for rounds until WebView2Loader.dll was locked and really threw, then exploded; changed to `shutil.SameFileError`. Also moon test's CVT1100 (the test driver links moon's own MANIFEST duplicated with yue_mbt_manifest.res) reproduced locally; per CI convention the test gate carries `YUE_MBT_SKIP_MANIFEST=1`; application builds keep the manifest unaffected. Verification: 33/33 + both example builds/smoke alive; the outside-click interaction pending real-machine re-verification (with select/dropdown/calendar/color-picker open, clicking blank page, the title bar, or another application window should collapse; clicking a row inside the popup still selects normally).
- **Splitter dragging dead, two root causes in a row: explicit SetCapture dismantling the implicit capture + flexbasis percentage strings not parsed (fixed 2026-09-19, synthetic drags verified, real machine re-verified)**: symptom: on Windows, dragging hsplit/vsplit's handle produced no reaction (the initial ratio was wrong too — the handle hugged the left instead of 50%). Diagnostic methodology: three stderr probe points in the shim (unbuffered; **MoonBit println is fully buffered under pipes and lost on taskkill — do not instrument with it**) + PowerShell synthesizing real drags (GetProcess MainWindowHandle -> GetWindowRect -> mouse_event/SetCursorPos) + before/after window-screenshot comparison (byte-identical screenshots = the frame didn't change; one look dispels "seemed to run but didn't"). Root cause one: libyue's Windows side **implicitly captures on press** any view with a mouse handler attached (EmitMouseClickEvent's implicit capture); the component then explicitly calling `SetCapture` triggers `WM_CAPTURECHANGED`, and `OnCaptureChanged` clears `captured_view_` — **the implicit capture dismantled by our own hand; the system-level ::SetCapture is still there but view-level routing is severed** — from then on, mid-drag moves get dispatched by cursor position to other views and the handle never hears from them again (probe smoking gun: HasCapture before=1 / after=0 / system capture=1). Fix: `yue_mbt_view_set_capture`'s Windows branch gained a guard — skip the redundant set when capture is already held (the GTK side's capture is a per-control grab with no such conflict; direct call kept). Root cause two: the `flexbasis:"50%"` percentage string is parsed only on the GTK side and silently ignored on Windows (the first pane compressed to its min width; the handle hugged the left); fix: after the splitter's first layout completes (post_task), convert to **pixels** from the actual size and write flexbasis, the same form as drag-time pixel writes — unified cross-platform. Verification: synthetic drag moved the handle 50% -> ~68% (matching the +120px synthetic displacement), screenshots confirm the panes actually changed; gate 33/33 + both example builds/smoke. **Lessons: on Windows, when an "explicit capture" API coexists with implicit capture, check HasCapture before touching SetCapture; style strings (percentages/keywords) are GTK semantics — cross-platform components always use numeric pixels.**
- **Popup bubbles/dropdown backgrounds do not follow the theme (fixed 2026-09-19, synthetic clicks verified)**: symptom: under the dark theme, popover_t's bubble was white on Windows — the text color followed via label_t's on_theme_change re-set all along, so white background with light text was unreadable; the same affected all Popover-hosting surfaces (select_t/dropdown_menu/calendar_t/date_picker_t/color picker). Root cause: on Linux, popups live inside the application window system, and the global takeover CSS's `window { background-color }` rule covers them; the Windows replacement popup is an **independent bare nu::Window** with no application-level CSS — a default white background nobody manages. Fix (full-chain new `Popover::set_background_color`, shim->header->ffi->method): the shim's `yue_mbt_popover_set_bg` — Windows sets the replacement small window's background color, Linux/mac are no-ops (CSS already covers); the component layer's `bind_popover_bg` (sets theme_bg_panel + subscribes to on_theme_change to re-set) wired into all 5 Popover creation points. Verification: dark-theme minimal example + PowerShell synthetic click on "open bubble"; screenshots confirm the bubble's dark background with clearly readable light text, stylistically consistent with the main window; gate 33/33 + both example builds/smoke. Methodology on record: **always write tool-generated .ps1 scripts with English comments — Chinese comments in BOM-less UTF-8 get misread as ANSI by PowerShell 5, producing bizarre parse errors disguised as strange Bitmap constructor exceptions — extremely time-consuming to debug**.
- **dialog could not be closed and clicks passed through the mask: Windows hit-testing and painting order run in opposite directions (real-machine feedback 2026-09-19, synthetic clicks verified, fix shipped with fork v0.15.6-mbt.6)**: symptom: after dialog_t popped, the X/cancel/confirm all did nothing, and one could click the main UI's buttons straight through the full-screen mask (the visual mask existed; events behaved as if it didn't). Root cause: libyue Windows's `ContainerImpl::FindChildFromPoint` iterates children **in add order, forward**, taking the first child containing the point, while `ContainerImpl::Draw` likewise paints forward (later additions painted on top) — **hit priority and paint layering are exactly opposite**: for later-attached window roots like dialog/toast, the absolute mask visually covers the window, yet mouse hits always yield to the earlier-attached main layout container — events pass through to "below"; the buttons inside the panel likewise receive nothing, and the close path fails as a whole. On GTK, events are dispatched natively by GDK (upper widgets first); the two ends differ, so Linux never exposed it. Retrospective: the earlier "carousel right arrow mostly unresponsive" (100d008) was another symptom of the same root cause (the absolute panel's overflow area stealing the arrow's hits), worked around via layout back then without touching the essence. Fix: fork `51fabe6f` — `FindChildFromPoint` iterates in reverse (`adapter_->ForEach(callback, /*reverse=*/true)`), aligning hit order with paint layering; non-overlapping siblings are unaffected (the reverse first hit equals the forward one); in overlapping scenarios the later-added (visually on top) wins, semantics aligned with GTK. The compile path for immediate local verification (reusable for subsequent fork patches): **this machine lacks gn/depot_tools and cannot build the bare fork tree; the CMake chain consumes the release dist structure, and the nativeui source inside the package is a jumbo merged file (no individual files to replace)** — download the previous source dist, patch the same function inside `nativeui_jumbo_*.cc`, `cmake -S fork/scripts/prebuilt -DDIST_DIR=<dist>` to build yue.lib, and backfill `build/yue_prebuilt.lib` and `lib/windows-x64/`; the official archival goes through a fork commit + tag + CI packaging (prepare.py's version and sha256 upgrade along; the local manual backfill gets overwritten and aligned by the official package). Verification: the diagdlg minimal example (a background button counting pass-throughs) with synthetic clicks — with the mask open, clicking the "background button" position -> the mask collapses (close_on_mask works), pass-through count 0; reopening and clicking "delete" -> collapses and on_confirm fires; gate 33/33 + both example builds/smoke. **Lessons: whenever "the visually-on-top view receives no events / clicks pass through", first check whether the hit-traversal direction matches the paint order; GTK being fine does not mean Windows is fine — the two ends' dispatch mechanisms were never the same to begin with**.
